# Cloudreve Pro v4.18.0 分享权限机制分析与实测结论

> 分析对象：15213 实例上运行的官方 Cloudreve Pro v4.18.0（master 模式）
> 方法：二进制静态分析（符号、调用关系、字符串常量）+ 隔离实例实测
> 约束：全程只读分析线上二进制与线上库；所有写操作只在隔离测试实例（副本库 + 独立端口）上进行

---

## 一、结论摘要

1. **「分享仅查看」这个设置在本版本里没有任何服务端效力。** 前端有完整的权限设置 UI，但用户选定的权限**根本不会写入数据库**：无论怎么设置，`shares.permissions` 落库永远是 `null`。
2. **即使手工把权限写进数据库，后端也不读。** 实测把「匿名仅可读」直接写进 `shares.permissions` 后重启实例，匿名访客拿到的能力集与宿主完全相同，写操作照旧成功。
3. **根因不在根源假设所指的位置。** 本次任务原先的核心假设是「`file_ancestor_permissions` 表为空导致校验退化为全放行」。实测与静态分析均表明：该表**与分享写权限判定毫无关系**，填充它对封堵分享写操作无效。
4. 实测确认：匿名访客在「仅查看」分享下**新建目录、重命名、删除、上传四项全部成功**，且删除操作对宿主原有文件同样生效。
5. 在不升级、不改二进制的前提下，**网关层拦截是唯一可落地的封堵手段**（详见第五节）。

## 二、Pro 的分享权限模型（机制描述）

### 2.1 数据结构

分享记录在数据库的 `shares` 表中保存一个名为 `permissions` 的 JSON 字段。该字段按「访问者与宿主的关系」分四类主体，各存一组权限位：

- `everyone` — 所有访问者
- `same_group` — 与宿主同用户组者
- `other` — 其他已登录用户
- `anonymous` — 未登录的匿名访客
- `user_explicit` — 额外指定的个别用户

每组权限位是 5 个开关：**读取、更新、新建、删除、转分享**（按此顺序对应位 0～4）。这组位以紧凑字节串（base64 呈现）表示。

### 2.2 与「能力集」的区别

系统内部另有一套**细粒度操作能力集**，包含二十余项操作（新建文件、重命名、设置权限、移动到我的空间、移动到回收站、上传、下载、列目录、生成缩略图、加锁等）。接口返回给前端的 `capability` 字段（本次观测到的值形如 `39/9AQ==`）指的是**这一组**，不是分享权限位。

两套东西不是一回事：分享权限是「谁能做什么」的业务规则，能力集是「这个会话被允许调用哪些操作」的执行层凭据。本版本的缺陷正在于——**能力集从不参考分享权限**。

### 2.3 判定链路

分享访问时的实际判定顺序是：

1. **分享准入**：只检查账号级布尔开关的第 7、8 位（「是否允许访问分享链接」这类全局账号策略）。不通过则提示无权访问分享链接。**这一步与分享自身的权限设置无关。**
2. **能力集装配**：装配出的能力集是**一组固定常量**，与分享配置、访问者身份均无关。因此匿名访客、宿主、其他登录用户拿到的能力集完全一致。
3. **目录内容过滤**：读路径上存在一个基于分享权限的过滤器，但它只影响「列目录时能看到什么」，不参与任何写操作的许可判断。
4. **写操作执行**：新建、重命名、删除、移动/复制四条写路径内部**没有任何分享权限或能力检查**，直接执行。

也就是说，一旦通过了第 1 步的账号级准入，后续写操作畅通无阻。

### 2.4 关于 `file_ancestor_permissions` 表

该表存放「文件 → 祖先目录」的权限继承关系，**只在文件上传的预校验环节被读取一次**（用于判断上传目标路径沿途是否有拒绝上传的祖先目录），**不参与分享场景下的写权限判定**。

因此：**填充这张表不能封堵分享写操作。** 本次任务原先的核心假设不成立，如实记录如下。

### 2.5 关于权限配置为何存不下来

接口层面确实是接收权限参数的（创建分享与更新分享的请求体都带该字段），但落库环节把它丢弃了：用空权限创建与用明确权限创建、更新，接口均返回成功，数据库字段一律保持 `null`。这属于**配置写入链路的缺陷**，而非「配置了但没生效」。

## 三、实测记录

### 3.1 环境

- 测试实例：生产库副本 + 独立端口，与 15213 完全隔离；`file_ancestor_permissions` 保持与生产一致的空白状态。
- 测试对象：由宿主在测试实例上新建目录 `acldir`，并以其创建分享（权限参数按「匿名仅可读」构造）。
- 访问方式：不携带任何登录凭据的匿名 HTTP 请求。

### 3.2 分享建立与权限落库

| 操作 | 接口结果 | 数据库 `permissions` |
| --- | --- | --- |
| 创建分享（权限传空） | 成功 | `null` |
| 创建分享（权限传「匿名仅可读」） | 成功 | `null` |
| 更新分享（权限传「匿名仅可读」） | 成功 | `null` |

### 3.3 匿名访客写操作（四项）

| 项目 | 结果 | 说明 |
| --- | --- | --- |
| 新建目录 | **成功** | 匿名创建 `anon-new` |
| 重命名 | **成功** | 匿名把 `anon-new` 改为 `anon-renamed` |
| 删除 | **成功** | 先删自己建的目录，随后**把宿主原有的 `sub1` 目录也删除成功** |
| 上传 | **成功** | 匿名上传 `anon.txt`（5 字节），列表可见、大小正确 |

四项全部成功，未出现任何拒绝提示。

### 3.4 匿名与宿主能力集对比

匿名访客列目录时返回的能力集为 `39/9AQ==`，与宿主登录后拿到的值**完全相同**。这是「匿名被当作宿主」在数据上的直接体现。

### 3.5 手工写入数据库后的对照实验

为区分「只是没存」与「存了也不读」，在隔离副本上直接把 `shares.permissions` 改为「匿名仅可读」，重启实例后再测：

- 匿名访客拿到的能力集：仍为 `39/9AQ==`，与宿主一致。
- 匿名新建目录：**仍然成功**。

结论：**后端读路径不消费该字段，写路径也不校验它。** 手工补数据无法修复。

## 四、与既有两份报告的关系

- **#72 报告的根因定位（后端写权限判定沿用了继承自父目录的能力集，而非分享解析出的能力集）方向正确**——本次静态分析确认写路径上不存在分享权限检查，与「能力盖章早于分享解析、写判断只看继承字段」一致。
- **#73 报告记录的几项观测全部复现且成立**：`shares.permissions` 与 `files.permissions` 均为 `null`；往 `props` 注入 `allow_upload`/`allow_edit` 无效；二进制中不存在 `allow_upload`/`allow_edit`/`preview_only`/`upload_only` 这类字符串；匿名返回的能力集与宿主相同；匿名删除/建目录/重命名实测成功；分享根目录自身重命名被拒（返回不支持的操作）。
- **本次新增的两点**：
  1. 权限设置**在落库环节就被丢弃**（传了明确权限也是 `null`），这比「注入了但没生效」更靠前一层。
  2. 手工把权限写进数据库**依然无效**，证明问题出在读取与校验环节，而非存储环节。
- **需要更正的一点**：`file_ancestor_permissions` 表与分享写权限**无关**，它只服务上传预校验。填充该表封堵写操作的想法不成立。

## 五、可落地的封堵方案（不升级、不改二进制）

由于缺陷在程序内部且无法通过配置或补数据修复，唯一可行手段是在**反向代理层拦截**。

判据需同时满足以下三条，才判定为「匿名访客对分享目录的写操作」并拒绝：

1. 请求方法是写操作：`POST`、`PUT`、`PATCH`、`DELETE`。
2. 请求体中的目标 URI 指向分享空间（形如 `cloudreve://<分享ID>@share/...`）。
3. 请求**不带**登录凭据（无 `Authorization` 头）。

这三条同时成立时，请求必然来自匿名访客对分享内容的写操作，应直接拒绝。

### 5.1 为何这三条足够精准

- **不误伤宿主与其他登录用户**：任何已登录用户的请求都带 `Authorization` 头，第三条不成立，直接放行。
- **不误伤匿名读取**：读取走 `GET`，第一条不成立，放行。
- **不误伤登录、上传等正常流程**：这些请求的目标 URI 不在分享空间内，或带凭据，至少一条不成立。

### 5.2 已验证的效果

#73 阶段已对该方案做过实测：四项写操作（新建、重命名、删除、上传）全部被拦住，宿主操作零误伤，匿名浏览列表仍正常放行。

### 5.3 需要注意的边界

- 拦截依赖请求体中的 URI 特征，因此代理必须能读取请求体（注意请求体大小上限与缓冲配置）。
- 若将来升级到修复了该缺陷的版本，此规则应移除，以免与程序自身的权限控制叠加。
- 该方案是**兜底**，不是修复：它拦住的是「匿名写分享」，不改变程序内部「匿名等同于宿主」这一事实。

## 六、建议

1. **短期**：在 15213 前置反向代理上启用上述拦截规则，作为止血措施。
2. **中期**：向 Cloudreve 官方反馈本缺陷，核心是三点——分享权限不落库、能力集装配不参考分享配置、写路径无分享权限检查。
3. **长期**：升级到修复版本后移除代理层规则。是否升级由使用者决定，本次分析未改动任何生产二进制。
