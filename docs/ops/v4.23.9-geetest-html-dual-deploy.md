## 一、问题一：极验通过后仍提示「验证码错误」

### 1.1 现象

后台已开启极验（`captcha_type=geetest`），前端滑块能正常加载、能通过挑战，但提交注册 / 找回密码 / 举报时提示「验证码错误」（服务端 `code=40026`）。两台实例现象一致。

### 1.2 根因（已真机确认，非推测）

服务端二次校验用了**已经不存在的旧端点**：

| 项目 | 内容 |
| --- | --- |
| 代码原请求 | `https://api2.geetest.com/v4/validate.php`，回退 `https://api.geetest.com/v4/validate.php` |
| `api2.geetest.com` 解析 | **NXDOMAIN**（该域名已不存在） |
| `api.geetest.com/v4/validate.php` | 被上游 WAF 拦截，返回 **HTTP 567**（155 实测）／**405**（B 实测）的 HTML 拦截页 |
| 正确端点 | `https://gcaptcha4.geetest.com/validate`（**没有** `/v4/` 段，form POST，`captcha_id` 放在 query），备用 `https://gcaptcha4.geevisit.com/validate` |

因为拿到的永远是拦截页 HTML 而不是极验的业务 JSON，`Verify()` 一律返回失败 —— 前端就显示「验证码错误」。**这是服务端的问题，与用户操作、浏览器、网络都无关。**

### 1.3 修复

`pkg/geetest/client.go`：

1. `validateEndpoints` 改为官方地址 `gcaptcha4.geetest.com/validate` + `gcaptcha4.geevisit.com/validate`。
2. 新增 `looksLikeJSON()` 守卫：当上游返回的不是 JSON（例如被 WAF/CDN 换成拦截页）时，视为「该端点不可用」并尝试下一个端点，而不是把它当成「验证码不对」上报。这样以后再遇到上游拦截，日志里会明确体现为端点故障，不会被误判成用户的验证码错误。

`pkg/geetest/client_test.go`：更新端点断言，新增 `TestDefaultEndpointsAreOfficial`、`TestVerifySkipsWAFInterceptionPage`。`go test ./pkg/geetest/` 全部通过。

**影响范围**：只有后端，前端无需改动。

### 1.4 覆盖的极验入口（5 处，全部走同一个 `geetest.Verify`）

| # | 入口 | 路由 | 开关 |
| --- | --- | --- | --- |
| 1 | 账号密码登录 | `POST /api/v4/session/token` | `login_captcha` |
| 2 | 短信验证码发送 | `POST /api/v4/session/sms/send` | `login_captcha` |
| 3 | 注册 | `POST /api/v4/user` | `reg_captcha` |
| 4 | 找回密码（发信） | `POST /api/v4/user/reset` | `forget_captcha` |
| 5 | 举报滥用 | `POST /api/v4/abuse/report` | `abuse_captcha` |

后台「人机验证」页的四个勾选项（登录 / 注册 / 找回密码 / 举报）分别对应前四类。

### 1.5 真机验证（155.117.85.143，v4.23.9 运行中）

**端点层面**——服务端日志显示请求已打到正确地址并得到极验正规应答（HTTP 200 + 业务 JSON，不再是 WAF 拦截页）：

```
POST "https://gcaptcha4.geetest.com/validate?captcha_id=949c66…"  →  200  (83ms)
POST "https://gcaptcha4.geetest.com/validate?captcha_id=949c66…"  →  200  (66ms)
```

**五个入口逐个实测**（开关保持生产原值，除登录为验证开关语义而临时开启后已恢复）：

| 入口 | 结果 | 判读 |
| --- | --- | --- |
| 注册 `POST /user` | `40026 CAPTCHA not match.` | 已进入极验业务校验，伪造票据被拒 —— 正确 |
| 找回密码 `POST /user/reset` | `40026 Verification failed` | 同上 —— 正确 |
| 举报 `POST /abuse/report` | `40026 Verification failed` | 同上 —— 正确 |
| 登录（`login_captcha=0`） | `40080 Incorrect password` | 开关关闭时正确跳过极验 |
| 登录（临时 `login_captcha=1`） | `40026 CAPTCHA not match.` | 开关开启时正确要求极验 |
| 短信发送（`login_captcha=0`） | `40019 SMS sign-in is not enabled` | 正确跳过极验 |
| 短信发送（临时 `login_captcha=1`） | `40026 CAPTCHA not match.` | 正确要求极验 |

**开关语义**：设置项改了之后清掉 Redis 缓存立即生效，无需重启服务。

**关键判据**：修复前，这五个入口必然 100% 失败（端点根本不存在或被拦）；修复后，它们全部走到了极验的业务校验逻辑，并如实反映票据真伪。修复前是「永远失败」，修复后是「票据对就通过」。

### 1.6 关于「滑块自动化通过」的说明（如实记录）

本报告中的入口验证使用的是**伪造票据**，用来证明「校验链路是否连通、判据是否正确」。要验证「真人滑块通过后整条业务链路走通」，需要在浏览器里真正完成极验滑块。

验证过程中尝试用浏览器自动化（Playwright）完成滑块，**极验的反机器人检测会拒绝自动化轨迹**（表现为反复「Please try again」）。这是极验的设计，不是本项目的缺陷，也无法绕过。因此**真人滑块通过后的发信/改密全流程，需要您在浏览器里手工点一次确认**——这是目前唯一诚实的验证方式。

## 二、问题二：站点公告支持 HTML 格式

### 2.1 需求与安全前提

公告需要能展示格式化内容（标题、加粗、列表、链接等）。公告对**所有登录用户可见**，一旦允许 HTML，就必须防止 XSS（否则一个恶意公告等于给所有用户投毒）。因此采用**白名单过滤**，而不是「允许全部标签再逐个黑名单」。

### 2.2 白名单范围与理由

允许的标签（`pkg/htmlsafe/htmlsafe.go`）：

`p, br, h1–h6, strong, b, em, i, u, s, del, ins, blockquote, code, pre, ul, ol, li, a, img, hr, span, div, table, thead, tbody, tr, th, td, figure, figcaption, sub, sup, small`

允许的属性：
- 任意元素：`class`、`title`
- `<a>`：`href`、`target`、`rel`（强制加 `rel="noopener noreferrer"`）
- `<img>`：`src`、`alt`、`width`、`height`
- `<td>/<th>`：`colspan`、`rowspan`

**一律禁止并移除**：
- `<script>`、`<style>`、`<iframe>`、`<object>`、`<embed>`、`<form>`、`<input>` 等可执行 / 可注入内容的标签
- 所有 `on*` 事件属性（`onclick`、`onerror`、`onload`…）
- `href` / `src` 中的 `javascript:`、`vbscript:`、`data:` 等危险协议
- `style` 属性（含 `expression()` 等历史攻击面，且与主题样式冲突）

理由：公告是**纯展示**内容，上面保留的标签足以表达排版需求；凡是不用于展示的标签和属性一律不放行。宁可少一个效果，不冒一个 XSS 的风险。

### 2.3 实现（三层防护）

| 层 | 位置 | 作用 |
| --- | --- | --- |
| 写入时清洗 | `service/admin/site.go` → `announcementPreProcessor` | 后台保存公告时清洗，脏数据不落库 |
| 读取时清洗 | `pkg/setting/provider.go` → `sanitizeLocalized("announcement", …)` | 返回给客户端前再清洗一次，覆盖历史脏数据与多语言变体（`announcement_i18n`） |
| 前端二次过滤 | `frontend/src/component/Common/SafeHTMLContent.tsx` | 浏览器端用同规则再过滤一次后才 `dangerouslySetInnerHTML` |

**为什么三层**：写入层保证数据干净；读取层保证即使有人直接改库或走别的写入路径也安全；前端层是最后一道，防止服务端被绕过。任一层单独失守都不会导致 XSS。

前端另有两处配合改动：
- `AnnouncementDialog.tsx`：含标签的内容走安全渲染，**旧的不带标签的纯文本 / Markdown 公告继续走原来的渲染方式**（向后兼容，不会把已有公告显示成乱码）。
- `SiteInformation.tsx`：公告输入框加高，下方增加**实时预览**，管理员能直接看到最终效果。

### 2.4 真机验证（155.117.85.143，v4.23.9 运行中）

提交一段同时包含正常格式与多种攻击载荷的公告：

```html
<h2>系统维护通知</h2><p>美国节点 <strong>11月15日</strong> 后恢复。</p>
<ul><li>请勿上传新文件</li></ul>
<script>alert(document.cookie)</script>
<img src=x onerror=alert(1)>
<a href="javascript:alert(2)">点我</a>
<iframe src="https://evil.example"></iframe>
<p style="color:red">红色文字</p>
```

**数据库实际存储 / 接口返回的内容**：

```html
<h2>系统维护通知</h2><p>美国节点 <strong>11月15日</strong> 后恢复。</p>
<ul><li>请勿上传新文件</li></ul>
<img src="x"><a>点我</a><p>红色文字</p>
```

逐项判读：

| 载荷 | 结果 |
| --- | --- |
| `<script>alert(document.cookie)</script>` | 整个标签被删除 |
| `<img onerror=alert(1)>` | 标签保留，`onerror` 被移除 |
| `<a href="javascript:...">` | 链接保留、文字保留，危险 `href` 被移除 |
| `<iframe src=evil>` | 整个标签被删除 |
| `style="color:red"` | 属性被移除（按白名单设计） |
| `<h2> <strong> <p> <ul> <li>` | **全部保留** |

**前端渲染**（真实浏览器登录后查看公告弹窗）：

- 显示为「系统维护通知」大标题 + 加粗的「11月15日」+ 项目符号列表 —— 格式正确
- 页面**没有弹出任何 alert 对话框**（监听了浏览器 dialog 事件，计数为 0）—— XSS 被拦截
- 公告弹窗正常出现，可关闭

**向后兼容**：验证前站上原有的是不带任何标签的纯文本公告，切换后显示正常（见 2.3 的兼容逻辑）。

### 2.5 测试数据处理

验证用的临时管理员账号已在验证结束后删除（含其同名文件记录），公告已恢复为验证前的原文。生产上真实用户的账号与密码全程未触碰。

## 四、已知限制

1. 极验滑块的真实人工通过无法自动化验证，需在浏览器手工确认一次（见 1.6）。
2. `style` 属性被白名单排除，因此公告中**不支持自定义颜色 / 字号**。如需该能力，应另行设计（例如限定 CSS 变量或预设主题类），不应直接放开 `style`。
3. 公告 HTML 仅在登录后弹窗与后台预览处渲染；其他位置的公告若有引用，需另行确认。
