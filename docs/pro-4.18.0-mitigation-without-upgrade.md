# 不升级 v4.18.0 前提下封堵分享权限漏洞的可行性评估

评估日期：2026-11-05。目标实例：InstaBox 15213 复制实例（官方 Cloudreve Pro **v4.18.0**，master 模式，`/data/pro15213/`）。

输入：[#72 排查报告](./pro-share-guest-permission-issue.md)（分支 `tds/conv-01a1acb9-c121-76ad-9fd5-383e9dcf41c2`）。

## 一、结论先行

### 1. 用户的问题：「能不能从数据库入手修复？」

**不能。** 不是「改起来麻烦」，而是**数据库里根本不存在可改的那份数据**。

「访客仅查看」这条设置在 15213 的库里没有任何落点：`shares.props = {}`、`shares.permissions = null`、`files.permissions = null`、`file_ancestor_permissions` 空表。也就是说，这条分享和一条「完全放开」的分享**在数据库里长得一模一样**，没有任何字段能表达「这条是只读的」。

进一步的实测（第三节）表明：**即使手工把 `allow_upload/allow_edit=false` 硬塞进 `props` 列，程序的放行结果也不会有任何变化**——因为这个 Pro 二进制根本不读这些字段。

> 一句话：数据库不是「配置错了」，而是「从来没存过这份权限」。改无处可改。

### 2. 同一条路上并行的问题：#72 报告的根因定位对 15213 **不成立**

这一点必须先纠正，否则后面的修复方向会全错。#72 报告把根因归到本仓库 fork 的 `share_navigator.go:202/241` 与 `newFile()`（`file.go:348`）的父子能力集继承。**该定位在 fork 代码里成立，但不是 15213 这个二进制的实际情况**，理由见第二节实测。

### 3. 不改二进制的可行替代：网关层拦截，实测有效

在 nginx/openresty 层按「**写方法 + 请求体含 `cloudreve://<id>@share` + 无 `Authorization` 头**」三个条件联合判定，可以做到：

| 项 | 匿名访客 | 结果 |
|---|---|---|
| 新建文件夹 | `POST /api/v4/file/create` | **403 拦住** |
| 删除 | `DELETE /api/v4/file` | **403 拦住** |
| 重命名 | `POST /api/v4/file/rename` | **403 拦住** |
| 上传（建会话） | `PUT /api/v4/file/upload` | **403 拦住** |
| 移动 / 复制 | `/file/move`、`/file/copy` | **403 拦住** |
| 正常浏览列表 | `GET /api/v4/file` | **200 放行**（不能误伤） |
| 宿主本人写（带 token） | 任意 | **200 放行**（零误伤） |
| 其他已登录用户写 | 任意 | **200 放行**（零误伤） |

并且这个方案能可靠区分「匿名访客」与「宿主本人 / 任何已登录用户」——靠的是**请求有没有 `Authorization` 头**，这是确定性判据，不是猜测。

## 二、核实 #72 报告的前提（实测，非引述）

### 2.1 复现成功：前提成立

在 15213 上建测试目录 `share-probe-1`、"仅查看"分享 `1ytW`，然后**不带任何 Cookie/Token** 直接打接口：

```
匿名列分享目录  → parent.capability = "39/9AQ=="   ← 与宿主完全相同的能力位串
匿名建目录      → {"code":0,...}  成功，目录真的出现
匿名重命名      → {"code":0,...}  成功
匿名删除        → {"code":0,"msg":""}  成功
```

四项里三项确认提权（上传见 2.3 说明）。**#72 的「漏洞存在」这一结论成立，且能在 15213 这个二进制上复现。**

### 2.2 但根因定位与 #72 不同：这个二进制不是 fork 的代码

对 15213 的二进制做符号表比对：

| 符号 | 本仓库 fork（4.23.x） | 15213 的 v4.18.0-pro |
|---|---|---|
| `shareNavigator.walkNext` | 有 | **有** |
| `shareNavigator.Capabilities` | 有 | **有** |
| `shareCapabilities` | 有 | **无** |
| `propsCapabilities` | 有 | **无** |
| `writePermitted` | 有 | **无** |
| `newFile`（dbfs 包） | 有 | **无** |

并且对整个二进制做字符串扫描，**完全找不到** `allow_upload` / `allow_edit` / `preview_only` / `upload_only` 这四个字段名。

也就是说：

- 15213 跑的不是「fork 合并了那个未合并 PR 的版本」，它有自己的分享实现（`shareNavigator` 存在但收窄逻辑不同）；
- #72 提的修复方案 A（改 `walkNext` 盖能力集）**无法适用于这个二进制**——那是改源码的方案，而 15213 没有源码、也不许换二进制。

**结论：#72 的「漏洞存在」可用；「根因在第 348 行 newFile 继承」这一条对 15213 不适用，后续任何基于「改那几行」的方案都无法落地到 15213。**

### 2.3 上传这一项的说明（诚实标注）

四项里上传无法在当前实例上给出干净的实测结论，原因是**实例的上传流程本身有故障**，与权限无关：

- 任何上传请求（管理员自己也一样）都返回 `40004 Object existed`；
- 换目录、换文件名、换账号都一样；
- 库里能看到大量 `sys:upload_session_id` / `sys:restore_uri` 的残留占位文件（含 #72 测试期留下的 `evil.txt`、`renamed.txt`、`sub/`、`x.txt` 等）。

所以「上传是否被拦」这一项，我只能给出**网关层能拦住建会话请求**（`PUT /api/v4/file/upload` 返回 403）的实测，以及「后端权限判定与建目录/删除共用同一放行逻辑」这一从「匿名建目录成功」推出的事实。**不把上传写成「已实测被后端放行」。**

顺带：#72 报告 §2.5 声称测试残留「已全部清除」，实际库中仍有 `guest-perm-test`/`perm-test-1106` 系列占位与文件。该说法不准确，但不影响主结论。

## 三、数据库方案的实测过程（在隔离副本上，未动线上库）

### 3.1 实验设置

- 用 `sqlite3 ".backup"` 导出 15213 的库（WAL 模式，直接拷主文件会损坏），复制二进制与 license 环境；
- 在 **127.0.0.1:15299** 起一个独立实例（与 15213 完全隔离，不占用其端口、不共享其库）；
- 所有改库实验只作用在这份副本上。

### 3.2 实验一：库里有没有权限字段

```sql
select id, props, permissions from shares;
-- 4 条分享全部:  props = {}   permissions = null
```

沙盒副本上注入明确权限后：

```sql
update shares set props='{"allow_upload":false,"allow_edit":false,"preview_only":false,"upload_only":false}' where id=4;
```

再打同样的匿名请求：

```
匿名建目录 → {"code":0,...}  仍然成功
列表能力位 → "39/9AQ=="      仍然全开
```

**结论：往 `props` 里写权限无效。** 这个二进制不读这些字段。

### 3.3 因此数据库方案不可行的三层原因

1. **没有字段**：「仅查看」与「全开」在库里无差别，无法表达意图；
2. **写了不读**：即使强行注入字段，程序也不采纳；
3. **没有开关**：这套判定是编译进二进制的逻辑，数据库不提供任何「关掉访客写」的配置项。

> 所以对「能不能从数据库入手修复」，技术结论是明确的 **不能**，而不是「需要更多工作量」。

## 四、真正可行的替代方案（不改二进制）

### 方案 A（推荐）：网关层按分享 URI + 匿名身份拦截写请求

**原理**：匿名访客访问分享时，请求体里的路径形如 `cloudreve://1ytW@share/...`；而宿主操作自己的文件是 `cloudreve://my/...`。叠加「请求无 `Authorization` 头」这一确定条件，即可精确识别「匿名访客的写操作」。

**实测配置**（openresty / nginx + Lua；15300 端口实测，未接 15213）：

```nginx
location /api/v4/file {
  access_by_lua_block {
    local m = ngx.req.get_method()
    if m == 'POST' or m == 'PUT' or m == 'DELETE' or m == 'PATCH' then
      local auth = ngx.var.http_authorization
      if auth == nil or auth == '' then
        ngx.req.read_body()
        local body = ngx.req.get_body_data() or ''
        if ngx.re.find(body, 'cloudreve://[A-Za-z0-9]+@share', 'ijo') then
          ngx.status = 403
          ngx.header['Content-Type'] = 'application/json'
          ngx.say('{"code":40004,"msg":"share write blocked"}')
          return ngx.exit(403)
        end
      end
    end
  }
  proxy_pass http://127.0.0.1:15213;
}
```

**实测结果**（全部经网关打后端，逐项）：

| 请求 | 期望 | 实测 |
|---|---|---|
| 匿名 `POST /file/create`（`@share`） | 拦 | **403** ✅ |
| 匿名 `DELETE /file` | 拦 | **403** ✅ |
| 匿名 `POST /file/rename` | 拦 | **403** ✅ |
| 匿名 `PUT /file/upload` | 拦 | **403** ✅ |
| 匿名 `POST /file/move`、`/file/copy` | 拦 | **403** ✅ |
| 匿名 `@SHARE`（大写变形） | 拦 | **403** ✅（正则加了 `i` 标志后） |
| 匿名 `GET /file`（浏览） | 放行 | **200** ✅ |
| 宿主 `POST /file/create`（带 token） | 放行 | **200** ✅ |
| 宿主带认证走 `@share` 路径 | 放行 | **200** ✅ |
| 其他已登录用户写 | 放行 | **200** ✅ |

**代价与限制（必须知道）**：

1. **误伤面**：凡是**未登录用户**对 `@share` 路径的写操作都会被拦。也就是说，**「允许访客上传/协作编辑」的功能会整体失效**——因为那类请求长的一模一样（匿名 + `@share`）。这是不换二进制前提下**无法区分的**：v4.18.0-pro 的二进制里没有可读取的分享权限位，网关也就无从判断「这条分享是允许写的」。
2. **适用范围**：只拦 `/api/v4/file` 下的写方法。若将来发现其它写接口（如 WebDAV、直链上传）也接受 `@share` 路径，需要逐条补。
3. **不是根治**：这是入口过滤，不是权限模型修复。任何新增的写接口都要同步加规则。
4. **需要重启网关**：nginx/openresty 配置生效要 reload；若 15213 目前是直连暴露、前面没有反代，则需要先加一层反代（会改变访问链路，需谨慎安排）。

### 方案 B（务实的组合拳，无需改任何程序）

在方案 A 之外，限缩风险敞口：

1. **不把可写存储策略上的目录做成分享**——尤其别分享包含重要文件的目录；
2. **已发出去的分享，若不需要被改动，直接删掉**（删除后匿名访问返回 404，本次实测确认）；
3. **定期看回收站**：出现自己没删过的文件即为访客操作痕迹；
4. 给分享加**密码**（本次未测密码分享下的提权，但密码至少把「拿到链接就能写」降为「拿到密码才能写」）。

### 方案 C：升级到含修复的版本

用户已明确不接受升级，此处仅作记录：本仓库 fork（4.23.x）里该缺陷的根因是 `newFile()` 的能力继承，可用 #72 报告的方案 A + C 修掉，但这需要**换二进制**，与用户诉求冲突。另外升级到官方 4.19.x 并不能修——那套协作分享功能来自未合并的 PR，4.19.x 根本没有。
