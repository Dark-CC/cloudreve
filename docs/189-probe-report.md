## 2. 本轮实测结论

### 2.1 凭据有效性 —— 有效（服务端认得）

用**伪造** cookie 与**真实** cookie 对比，错误信息不同，这是凭据有效的直接证据：

| 输入 | 服务端响应（脱敏） |
| --- | --- |
| `COOKIE_LOGIN_USER=AAAA`（伪造） | `{"errorCode":"InvalidSessionKey","errorMsg":"cookieUserSession is null or invalid, cookieUserSession=null"}` |
| `COOKIE_LOGIN_USER=<COOKIE_REDACTED>`（真实） | `{"errorCode":"InvalidSessionKey","errorMsg":"check ip error - curIp=..., cookiesIp=..."}` |

- 伪造值 → 服务端**查不到会话**（`cookieUserSession=null`）；
- 真实值 → 服务端**查到了会话**，只在最后一步 IP 校验失败。

> **结论**：凭据没有过期、没有被登出，服务端能够解出对应会话。**阻塞不在凭据，在网络出口。**

### 2.2 IP 绑定 —— 本轮的核心发现

真实凭据的错误信息给出了两端 IP：

| 项 | 值 |
| --- | --- |
| `cookiesIp`（凭据签发时的客户端 IP） | `2408:8215:5c00:9272:4493:97f5:884e:701d`（IPv6） |
| `curIp`（本次请求的出口 IP） | `2408:8215:5c00:9272::20e`（IPv6，直连）／`27.218.7.103`（IPv4）／`155.117.85.143`（经代理，香港） |

三个可用的出口**没有一个**等于 `cookiesIp`。

**逐条排除过的手段（全部实测）**：

| 尝试 | 结果 |
| --- | --- |
| 直连（默认 IPv6） | ❌ `curIp=...::20e`，不符 |
| 直连并绑定本机另一个 IPv6（SLAAC） | ❌ `curIp=...:6854:aaff:fe9c:987a`，不符 |
| 经代理 `192.168.31.200:1082` | ❌ 出口变成香港 IPv4 `155.117.85.143`，更不符 |
| 检查是否接受**同 /64 网段**而非精确 IP | ❌ 同网段也不放行，是**精确匹配** |
| 把 `cookiesIp` 临时加成网卡附加地址 | ❌ 地址可加但不具可路由性（出口请求失败），**已立即移除，地址表已恢复原状** |
| 走凭据签发主机（同局域网 `192.168.31.199`）中转 | ❌ 该主机未开任何可用代理/SSH 端口 |

**`cookiesIp` 的归属**：通过 IPv6 邻居表确认 `2408:8215:5c00:9272:4493:97f5:884e:701d` 对应 MAC `cc:28:aa:39:03:3e`，即局域网内 `192.168.31.199` —— **用户自己的桌面机**（ping 时延 8–13 ms，同一链路）。它不是远端 IDC，而是用户本地网络里的一台机器。

> 这解释了为什么「凭据已授权到位」仍跑不动：**授权到位的是「谁能读这个密钥」，但密钥内容本身绑定了另一台机器的出口 IP**。这两件事彼此独立。

### 2.3 问题 5 的补充结论：错误码的优先级

本轮发现失效判定有**两种不同的 `InvalidSessionKey`**，且优先级分明：

1. `cookieUserSession is null or invalid` —— 会话查不到（伪造/已登出/已过期）；
2. `check ip error - curIp=..., cookiesIp=...` —— 会话查到了，但 IP 不符。

> **对驱动的直接含义**：错误映射必须先判 `check ip error`（这是**部署环境**问题，重试无用，应报配置错误而非鉴权过期），再判 `cookieUserSession=null`（这才是真正的会话失效 → `serializer.CodeStorageAuthExpired` 40099）。两者混为一谈会让用户看到「登录已过期」，而实际原因是出口 IP 变了。

同时实测确认：**4 个 CDN 节点**（`240e:980:9a20:36::/64` 段内 4 个地址）行为一致，均返回 IP 不符，排除了「某些节点状态不同」的可能。

## 3. 探测脚本的迭代（`scripts/189probe/p189.py`）

在 #57 版本基础上做了四处修正，均已自测：

| 改动 | 原因 |
| --- | --- |
| **新增步骤 [0]：IP 绑定前置校验** | 原来直接进入换发流程，IP 不符时会以误导性的错误层层失败；现在第一步就判定并给出明确结论（`exit 6`） |
| **对瞬时 `cookieUserSession=null` 加重试（3 次退避）** | 实测该错误会**短暂**出现（服务端会话缓存抖动），重试后再下结论，避免把抖动误判成「凭据无效」 |
| **`listFiles` 只取 `type=file` 的条目** | 根目录常只有文件夹，原实现可能拿到文件夹 id 而去请求下载地址 |
| **TTL 观测改为真实累积计时** | 原实现把 300/900 s 都压成 60 s 等待，等于没有测 TTL；现按 `0/60/300/900` 真实等待，并支持 `TTL_SCHEDULE` 覆盖 |

自测结果：

| 用例 | 结果 |
| --- | --- |
| 无凭据 | `exit 2`，不发起任何请求 |
| 凭据存在但 IP 不符 | `exit 6`，输出 `BLOCKED` 与所需条件 |
| 凭据泄漏检查 | 输出中真实凭据片段出现次数 = **0** |
| 语法 | `ast.parse` 通过 |

## 5. 下一步：需要用户做一件事

四项实测**在现有环境下无法推进**，缺的不是权限也不是密钥，而是「从凭据签发 IP 出网」。可选路径（按推荐度）：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）在用户桌面机重取 cookie 并在该机执行探测** | 在 `192.168.31.199` 上重新登录 `cloud.189.cn`，把新 cookie 更新到密钥，并让探测脚本在该机运行 | 需该机能跑 python3；一次性 |
| **B 让本机出口 IP 与凭据一致** | 在 `192.168.31.199` 上开一个 SOCKS5/HTTP 代理（只监听局域网），探测走它 | 需用户开代理端口；本机与桌面机必须同时在网 |
| **C 换一个不绑定 IP 的凭据形态** | 走 `api.cloud.189.cn` 的 `sessionKey`/`sessionSecret` 签名路径（该路径**不校验 IP**，只校验签名） | 需先拿到 sessionKey/Secret，而换发入口正是被 IP 挡住的那一步 —— 除非用户能从浏览器里直接取到这两个值 |

> **C 值得注意**：`api.cloud.189.cn` 只认 HMAC 签名、错误信息中从未出现 IP 相关字段。若用户能从已登录的浏览器里直接导出 `sessionKey` 与 `sessionSecret`（或在桌面机上跑一次换发），则后续实测可完全绕开 IP 绑定。这可能是成本最低的出路。
