# 从零自研网盘：功能清点与分期总方案

> 交付对象：决定「另写一套同技术栈网盘、以后替换生产站」的决策人
> 编写日期：2026-11-08（2026-11-08 晚按用户决策修订）　|　性质：**方案，不含实现代码**　|　配套文件：[`docs/api-contract.md`](./api-contract.md)（后端接口契约，前后端并行开发的锚点）
> 参照系：官方文档（本仓 `docs/zh/`）+ 活体 Pro 实例（Baixiong `127.0.0.1:15300`，`4.19.1-pro`）+ 现有 fork（本仓，`4.23.9`）+ 生产站实测数据（`pan.cdn.ad`，`4.23.9`）

---

## 0. 一句话结论与已定的三项决策

**结论**：这件事可做，而且最大成本不在「写功能」，在**像素级复刻 Cloudreve Pro 的界面与交互**以及**无缝接管现有 63 万实体文件、359 个分享、249 个 WebDAV 账号**。方案把「协议与数据」对齐现有系统（这样老数据、老分享链接、老客户端全部继续可用），把「界面」以活体 Pro 为像素基准反推，分期交付：**3 天内给你一个能登录、界面已是 Pro 样子的空壳测试版；7~10 天给你能上传下载分享的第二版；第 3 周具备接管生产的能力。**

**用户已确认（2026-11-08 晚，原话：「前期暂不开源，可以接受停机切换，可以接受这些功能先不做，但是后续要有」）**：

1. **前期不开源** ⇒ 只能走**完全独立实现**路线：新系统的代码自己写，**不得复制现有 fork 的任何函数**（fork 为 GPL-3.0，复制即被传染，见第 7 章）。读 fork 理解数据模型与协议、对齐格式与字段名仍然允许——这是兼容性需要。代价：相比「直接改 fork」，工作量约 **+30%**，已计入第 4 章的天数。
2. **接受停机切换** ⇒ 采用 **nginx 改一行端口 + 约 30 秒停机**（实测：优雅退出 11 秒、启动到监听 10 秒），不做双写双读。旧容器与旧库全程不动，秒级回滚。
3. **变现/社交登录/加密等先不做，但「后续要有」** ⇒ 这些功能**不进本期，也不是永久砍掉**：在分期里单列为 **P4「后续增强·已确认要交付」**，交付替换生产之后按优先级逐个补（第 4 章）。

> 尚未定、也不阻塞开工的：新代码放新目录还是独立仓库（不影响方案与工期，见第 8.1 节）。

## 2. 视觉与交互：像素级对齐 Pro 的执行方法（硬指标）

「和 Pro 一模一样」不能靠感觉，方案把它做成可验收的工程流程。

### 2.1 基准物：活体 Pro 实例

- 地址：`http://127.0.0.1:15300`（Baixiong 本机），版本 `4.19.1-pro`，已授权至 2027-02-06，systemd `cloudreve-pro15300.service` 常驻。
- 管理员：`/root/CloudrevePro/.admin_creds`（600，勿外传）。用它建测试用户、造样例文件/分享，才能截到「有内容」的真实界面。
- **它同时是接口基准**：本方案的 [`docs/api-contract.md`](./api-contract.md) 里每条请求/响应都是从这台实例上真实抓下来的（见该文件「抓取记录」）。

### 2.2 四层对齐物（每一层都要落到仓库里）

| 层 | 产物 | 存放 | 判定 |
|---|---|---|---|
| ① 结构层 | 每个页面的 DOM 骨架（标题、按钮、表格列、弹窗分区顺序） | `docs/ui-baseline/<页面>.md` | 与 Pro 同名元素一一对应，无缺失/无多余 |
| ② 样式层 | 关键元素的 `getComputedStyle` 快照：字体族/字号/行高/字重、padding/margin/gap、圆角、阴影、边框色、主色 | `docs/ui-baseline/styles.json` | 数值相等（允许 ±0px），颜色 HEX 相等 |
| ③ 像素层 | 截图（1440×900 / 1280×800 / 768×1024 / 390×844 四档 × 浅色/深色两主题） | `docs/ui-baseline/shots/` | `pixelmatch` 差异 < 0.5% 且无 >2px 位移 |
| ④ 行为层 | 交互脚本（点击路径 → 期望界面变化），如「上传中 → 进度卡片 → 完成 toast」 | `docs/ui-baseline/flows/` | Playwright 脚本对 Pro 与新系统双双跑通，结果一致 |

### 2.3 必对齐页面清单（第一批，按用户路径顺序）

1. 登录页 / 注册页（含极验挂载位置、错误提示气泡）
2. 主框架：顶栏（搜索、上传按钮、新建、头像菜单）、侧栏（首页/我的分享/分享给我/回收站/连接设备/管理后台入口）、面包屑
3. 文件列表：网格视图与列表视图、列头、行高、多选、右键菜单、批量操作条、空态、加载骨架
4. 上传：拖拽覆盖层、上传面板（进度、速度、剩余时间、暂停/取消、失败重试）
5. 文件详情/预览：图片全屏、视频播放器皮肤、PDF、代码预览
6. 分享弹窗（Pro 的权限折叠区是重点，见下）
7. 分享访问页（密码输入、目录浏览、下载按钮、过期态）
8. 我的分享列表、回收站、设置页、连接设备（WebDAV 凭据页）
9. 管理后台骨架：左侧分区菜单、仪表盘、用户表、策略表、组编辑

### 2.4 已知的 Pro / fork 界面差异（不做会「一眼不像」）

- **分享弹窗的权限矩阵**：Pro 4.19 的 `permissions` 是分主体结构（`everyone` / `same_group` / `other` / `anonymous` + `user_explicit` / `group_explicit`），UI 上表现为分组的权限条目与彩色标签；fork 用的是 5 个布尔开关。**新系统按 Pro 的结构做**，契约里已固化。
- 顶栏「上传」按钮是分裂按钮（主按钮 + 下拉选择目标目录）。
- 文件列表的 `capability` 是 boolset 编码串，前端据此灰掉不可用项——必须实现，否则右键菜单项状态与 Pro 不同。
- 主题色板来自接口 `site/config/basic` 的 `themes` 字段（MUI 调色板 JSON），前端不能硬编码。

### 2.5 防退化机制

- CI 里跑截图比对：任何页面像素差异超阈值即阻断合并，人工确认后更新基线。
- 视觉基线随每次「对齐新页面」扩张；基线文件进仓库，作为可审计的「像不像」证据。
- 禁止把 Pro 前端压缩产物（`/assets/index-*.js`）里的代码或资源直接搬进新仓库（法律与可维护性，见第 7 章）；对齐靠「观测值重写」。

## 3. 数据与无缝迁移

### 3.1 目标：老数据零改造接管

只要**表结构语义、ID 编码、密码哈希、对象键**四件事对齐，S3 上的 62 万实体一个字节都不用搬。

| 关注点 | 现有实现（已核实） | 新系统做法 |
|---|---|---|
| 库 | PostgreSQL 17，库名 `cloudreve_fork`，4.8 GB（剪裁后约 2.6 GB 有效） | 同 PG 17，同库名可换；表名/列名保持同义（不必逐字相同，迁移脚本做映射） |
| 文件模型 | `files`（树：`type/name/size/parent`，邻接表）+ `entities`（物理对象：`type/source/size/hash/storage_policy/upload_session`）+ `file_entities`（多对多，支持多版本/多实体） | 直接沿用三层模型——这是「一文件多版本、秒传去重、跨策略迁移」能成立的前提 |
| 对象键 | 由策略的 `dir_name_rule` / `file_name_rule` 展开，默认 `uploads/{uid}/{path}`，文件名默认 `{originname}` | 迁移时**沿用 `entities.source` 原值**，不重算键名；新系统只按策略凭据去同 bucket 读同一 key |
| 公开 ID | `go-hashids`，salt = `settings.hash_id_salt`，编码 `[id, type]`，type 常量顺序：`Share=0, User=1, File=2, Folder=3, Tag=4, Policy=5, SourceLink=6, Group=7, Entity=8, AuditLog=9, Node=10, Task=11, DavAccount=12, Payment=13, InvitationCode=14, Sku=15` | **必须逐字复刻**这套顺序与 salt；否则 359 条分享链接、16.9 万条直链、以及所有 `/f/`、`/s/` 外链全部失效 |
| 密码 | `salt(32) + ":" + hex(sha256(password + salt))`；兼容 v2 老格式 `md5:hash:salt`（`md5(salt+password)`） | **两种都实现**，登录时按前缀判定；用户无需改密 |
| WebDAV 密码 | `dav_accounts.password` 同格式 | 同步迁移并保留原密码 |
| 会话 | JWT（access/refresh），TTL 与 scope 在设置表 | 语义对齐即可，**旧 token 不强制兼容**（切换瞬间让客户端重登），但 `/api/v4` 路径与字段必须不变，否则桌面端/安卓端会崩 |
| 分享 | `shares`（密码、次数、过期、`props` 布尔位、`price_points`、`slug`）+ `share_files` / `share` 关联的文件 | 全字段迁移；`/s/<hashid>` 路由形式保持 |
| 直链 | `direct_links`（169,633 条，含下载计数、限速） | 全量迁移；`/f/<hashid>/<name>` 与 `/f/d/<hashid>/<name>` 两条路由保持 |
| 元数据 | `metadata`（91,363 条 `sys:*` + 数十万条 `exif:*`/`stream:*`） | 全量迁移（缩略图与媒体信息立即就有） |
| 组与配额 | `groups`（权限位 bitset、`max_storage`、`speed_limit`、`settings`、`storage_policy_id`）+ `group_allowed_policies` | 权限位用**同一套位序**，否则 637 个普通用户集体失去上传/分享能力 |
| 节点 | `nodes`（1 master + 3 slave） | 一期只迁 master；从节点在 P2 做离线下载时再接 |
| 不迁 | `audit_logs`（2.1 GB）、支付/积分/商品表（全空） | 不迁，切前导出一份冷备归档 |

### 3.2 迁移步骤（可在测试环境完整预演）

1. **导出**：`pg_dump -Fc` 生产库（现有流程已验证，注意下载链路 chunked 污染需解码，见 `docs/instabox-postgres-pro-fork-migration.md`）。
2. **结构与映射**：新系统 ent schema 建表 → 迁移脚本按映射表灌入（用户→组→策略→文件树→实体→分享→直链→元数据→WebDAV）。
3. **两条手工必做**（Pro→fork 迁移时踩过，会原样复现）：写入版本标记行（否则判空库建表 panic）；把**所有** identity 序列 `setval` 到 `max(id)`（否则读正常、写全撞 duplicate key）。
4. **对象存储连通**：14 条策略的 access key / endpoint / path-style / 自定义代理逐个试连，抽 20 个实体做 HEAD 校验大小。
5. **应用层验证**（第 3.3 节）。
6. **切换**：nginx 把 `pan.cdn.ad` 的 upstream 从旧端口改到新端口 + reload（**用户已确认接受停机切换**；实测整站停机约 30 秒，其中优雅退出 11 秒、启动到监听 10 秒）。旧容器与旧库**不动**，作为立即可用的回滚点。
7. **观察期 7 天**：旧站保持可切回；期间只读对比日志、错误率、下载 302 命中。

### 3.3 验证口径（不达标不许切换）

| 维度 | 口径 |
|---|---|
| 表级 | 用户/组/策略/文件/实体/元数据/分享/直链/WebDAV 逐表行数与 `sum(size)`、`max(id)` 与生产相等 |
| 用户级 | 随机 10 个真实用户 × 4 指标（文件数、目录数、字节数、实体数）逐项相等 |
| 内容级 | 随机 20 个跨策略实体真实下载，`sha256` 与生产一致；抽 1 个 Pro 时代老文件（防「多实体返回 0 字节」假象） |
| 分享级 | 随机 20 条分享：匿名访问信息 200、目录列得出、下载字节一致；加密分享密码解锁正常 |
| 直链级 | 随机 50 条 `/f/` 链接 302 到同源对象，字节范围（Range）请求正常 |
| WebDAV | 随机 5 个账号 `PROPFIND` 深度 1 列出内容与生产一致 |
| 回归 | 新系统自身：注册→登录→上传→下载→分享→回收站→恢复 全链路脚本通过 |

> 反例警告（团队实测过）：**不要用自己手工插入的测试记录判断迁移好坏**——手工插入的行缺关联会返回 0 字节，会误导数小时。

### 3.4 回滚

（切换方式已定为停机切换，因此回滚路径简单且可靠。）

- 一级：nginx 一行改回旧端口 + `reload`，秒级恢复（旧容器/旧库全程不动）。
- 二级：新库保留不动，回滚后仍可修复重试。
- 数据侧：切换前 `pg_dump` 冷备 + 策略凭据清单快照；S3 端只读，不存在数据被改写的风险（新系统上线初期**禁止**执行任何物理删除/回收站清理 cron）。

## 4. 分期方案（速度优先）

人力口径：按「1 名全职工程师」折算，团队里的 Agent 并行不改变关键路径依赖。每期都以「可点开、可演示」为完成标准。

### P0 · 骨架与像素地基（第 1~3 天）— 你要的「测试版 v0」

- 交付：登录页 + 主框架 + 文件列表（只读，样例数据）+ 分享弹窗静态版，**样式与 Pro 逐像素对齐**；后端登录/会话/站点配置/文件列表四个接口真跑。
- 依赖：无（先自建空库 + 本地上传策略）。
- 验收：`docs/ui-baseline` 里首批 6 张截图像素差异 < 0.5%；能登录、能看见自己的空空间。
- 风险点：MUI 主题与字体一致性（先对齐主题色板与字体栈）。

### P1 · 最小可用（第 4~10 天）— 「能登录、能上传下载、能分享」

- 交付：本地上传（分片 + 断点 + 进度面板）、下载/预览、新建/重命名/移动/删除/回收站、分享创建与访问页、我的分享列表、用户设置（改密、头像）。
- 依赖：P0 的契约（`docs/api-contract.md` 已给全）。
- 验收：用真实 200MB 文件跑通上传→秒传→下载→分享→匿名下载；中断续传成功率 100%。
- 风险点：分片与秒传的哈希口径；`capability` boolset 的正确性。

### P2 · 生产接管就绪（第 11~18 天）

- 交付：S3/KS3 等对象存储驱动（S3 兼容优先，13 条策略可接入）、直链 302 `/f/`、组与配额权限位、存储策略偏好与迁移、WebDAV 服务端、缩略图与 EXIF、管理后台（用户/组/策略/分享/文件/队列）、迁移脚本 + 验证脚本全套。切换方式已定：停机切换（第 3.2 节）。
- 依赖：P1 文件模型稳定；生产库导出。
- 验收：第 3.3 节**全部指标通过**，且在测试实例上完成一次「导入生产库 → 走完整验证」的演练。
- 风险点：**对象键与策略凭据**是唯一不可返工的硬约束，先做只读校验再谈写入。

### P3 · 完成度补齐（第 19~30 天）

- 交付：分享权限矩阵（仅预览/可上传/可编辑/投递箱）、离线下载（aria2 + 从节点）、Passkey、邀请码、事件与活动流、偏好设置全量、管理后台二期（事件、举报、批量操作）、性能与索引优化。
- 依赖：P2 的数据层。
- 验收：与 Pro 逐页对照清单全部打勾；压测（50 并发上传、200 QPS 列表）。

### P4 · 后续增强·已确认要交付（替换生产之后排期）

用户已确认这批功能「先不做，但后续要有」，因此它们不是可选项，而是**第二阶段的确定任务**，按「对现有用户的实际价值」排序：

| 顺序 | 功能 | 为什么要排在这里 | 依赖 |
|---|---|---|---|
| P4-1 | **文件加密**（策略级加密、`encrypt_metadata`） | 生产库已有主密钥但**没有策略开启**，所以替换时零迁移成本；上线后再开则需要迁移工具 | 对象存储驱动（P2） |
| P4-2 | **OIDC / SSO** | 生产当前关闭，但企业用户接进来时是刚需 | 会话与用户模型（P0） |
| P4-3 | **全文搜索**（索引 + 抽取） | 58 万文件的站，搜索体验是下一步最明显的短板 | 文件模型（P1）；可先接外部引擎 |
| P4-4 | **在线 Office 编辑（WOPI）** | 依赖外部 Office 服务，实施成本主要在部署侧 | 预览链路（P1） |
| P4-5 | **付费分享与积分体系** | 生产全为 0，但有商城/商品/订单表结构需要保留语义 | 分享权限矩阵（P3） |
| P4-6 | 微信 / QQ / 短信登录、邀请码体系 | 面向国内用户增长，量最大但最不紧急 | P4-2 的同一套认证抽象 |
| P4-7 | 桌面端 / 安卓端深度适配 | 客户端本体已在用，本期只保证接口不破（第 6 章） | 接口稳定性（全程） |

> 结论：**这些功能一条都不进 P0~P3 的关键路径**，但它们共享同一套数据模型与接口，所以实现时要预留扩展点（尤其是文件加密会改动实体与对象键、付费会改动分享访问链路），第 5.3 节已按此约束「可以读、不可抄」。

### 关键路径提示

- **前后端并行的前提是契约先冻结**：`docs/api-contract.md` 已经覆盖 P0/P1 全部接口，前端可以立即用 mock 开工，后端按同一文件实现。
- 视觉对齐与功能开发**互不阻塞**：前端先在 P0 把样式地基（主题、布局、组件库封装）钉死，后续每个页面才可能一次到位。

## 5. 技术选型建议

### 5.1 建议沿用现有 fork 的技术栈（有理由，不是惯性）

| 层 | 建议 | 理由 |
|---|---|---|
| 语言/框架 | Go 1.24 + Gin | 与参照系统同栈，接口语义、并发模型、流式下载/上传的坑已有现成答案；团队已有构建与发布链路 |
| ORM/数据层 | ent（代码生成） | 与现有库表结构一一映射，迁移脚本可复用字段语义；复杂关联（多对多 policy/entity）表达力够 |
| 数据库 | PostgreSQL 17 | 生产现役就是它；JSONB 用于策略设置/文件元数据，避免再引一套 NoSQL |
| 缓存/队列 | Redis（stream + 自研 worker） | 现有任务的语义（上传会话、秒传哈希、缩略图队列、回收站 cron）可直接照搬；不引 Kafka 这类重件 |
| 对象存储 | S3 兼容 SDK（minio-go）+ 各厂商适配器 | 现场 13 条策略里 12 条是 S3/KS3 形态；先做 S3 一家即可覆盖 99% 流量 |
| 前端 | React 18 + TypeScript + Vite + MUI v5 | **像素级复刻的唯一现实路径**：Pro 就是 MUI 主题驱动的界面，换框架等于重画一遍并保证不了「一模一样」 |
| 状态/请求 | Redux Toolkit + 自封装 fetch（`send()`） | 与 Pro 的请求/错误处理形态一致，好对齐 toast/重试行为 |
| 国际化 | i18next（中文为默认） | Pro 文案可直接对齐 key |
| 测试 | Playwright（端到端 + 视觉比对）+ Go 单测 | 视觉基线必须自动化，否则「像不像」无法验收 |

### 5.2 明确不建议的选项

- **换语言/框架（Node、Java、Python）**：与「同技术栈」的要求直接冲突，且把迁移风险从「协议对齐」放大成「协议 + 语义 + 性能」三重风险。
- **换 UI 框架（Ant Design / Element）**：像素级对齐会变成不可能任务。
- **微服务化**：单体 + 后台 worker 足够（生产当前 CPU 4%、内存 1.1 GB），拆了只会增加切换风险。

### 5.3 关于「从零」的范围界定（用户已定：前期不开源）

「从零另写」不等于「不能看现有代码」，但**看与抄的界线要划死**：

- ✅ 可以：读现有 fork 代码理解数据模型与协议；照抄**数据格式、路由形态、字段名、SQL 表列语义**（这些是兼容性契约，必须一致，照抄的是「规格」不是「代码」）。
- ❌ 禁止：把 fork 的函数体、结构体方法、前端组件实现搬进新系统。fork 是 **GPL-3.0**，一旦复制，新系统**必须**同样以 GPL-3.0 开源——与「前期暂不开源」直接冲突。
- ❌ 禁止：从 Pro 二进制/前端产物里提取代码或资源文件。
- ✅ 替代做法：用第 2 章的四层基线（结构 / 样式数值 / 像素 / 行为）反推界面，用 `docs/api-contract.md` 反推接口，用第 3 章的字段语义反推数据层——效果等价，且产出物天然是独立实现。
- 📌 对开发的实际影响：Go 侧的「现成答案」变为「现成的行为基准」，每个模块都要自己验证一遍（这部分工作量已计入 +30%）。

## 6. 客户端与接口兼容：留了什么余地

本期只做网页版，但同一仓库里的桌面端（Tauri）与安卓端会调同一个后端，替换生产时不能把它们打断。

1. **路径与字段不破**：统一 `/api/v4/...`，响应信封 `{code, msg, data, correlation_id}`，字段名与 Pro 一致（契约文件即为准）。这样现有客户端**零改动**可用。
2. **认证双轨**：JWT（access/refresh）+ OAuth2 授权码（第三方 App）+ WebDAV Basic。旧 token 不兼容是可以接受的，但刷新语义与 TTL 要对齐（`access_expires` / `refresh_expires`）。
3. **URI 方案复用**：`cloudreve://my/<path>`、`cloudreve://trash`、`cloudreve://<shareKey>@share/<path>`、`cloudreve://shared_by_me` 等，客户端大量依赖，必须原样实现。
4. **上传协议复用**：`PUT /file/upload` 建会话 → `POST /file/upload/{sid}/{index}` 传分片，响应里的 `upload_urls` 支持 S3 直传（客户端据此决定走直传还是中转）。
5. **明确不做的事**：新协议、新字段名、新路由前缀。任何优化都在 `v4` 语义内做。

## 7. 风险与法务

| 风险 | 说明 | 应对 |
|---|---|---|
| **GPL 传染** | 现有 fork 是 GPL-3.0。任何代码级复制都会让新系统必须 GPL-3.0 开源 | **已定：前期不开源 ⇒ 严格独立实现，禁抄函数体**（第 5.3 节）。审查动作：合并前对每个 PR 做「与 fork 的相似性自查」，尤其是 dbfs/hashid/权限相关的热门文件 |
| Pro 二进制边界 | Pro 是闭源商业软件；观测其界面与接口做兼容实现属独立开发，但提取代码/图片资源有风险 | 只用截图、计算样式、文案表；logo/图标自备 |
| 迁移不可逆 | 切换后新系统写入的数据老系统读不懂 | 切换后 7 天内不回写业务数据到旧库；一级回滚只到「切换瞬间」 |
| hashid/密码格式错位 | 一错，分享链接、直链、所有用户登录全废 | 契约里锁死；迁移做**逐条抽样比对**，不做「应该没问题」 |
| 对象键错位 | 下载全部 502/404，且排查极慢 | P2 先只读校验：随机 200 个实体按策略凭据 HEAD，全绿再谈写入 |
| 视觉反工 | 页面样式地基没钉死就开写页面，后面每页返工 | P0 必须先交样式地基 + 3 个页面基线截图 |
| 生产停机 | 实测 30 秒窗口 | 低峰切换；准备 5 分钟回滚演练脚本 |
